- 目标：降低 Alpha360 特征准备和训练的数据驻留峰值，恢复完整对照实验。
- 范围：数据读取、缓存与加载方式；保留特征定义、股票池规则、标签、时间切分、随机种子和模型参数。

## 1. 问题与证据

结构搜索已完成 Alpha158 的 12 组组合，随后在 Alpha360 特征准备阶段发生 OOM。尚未进入 Alpha360 模型训练，原始特征缓存也未生成。详见 [执行记录](execution-2026-09-04.md)。

诊断确认：

- 当前调用以 `instruments="all"` 读取整个快照，包含 4719 只证券、约 214.8 万行；每日股票池过滤发生在读取后。
- Alpha360 加标签所需的 `$close` 共 361 列，实际类型为 `float32`，单份数值矩阵约 2.89 GiB；两份约 5.78 GiB，均未计入索引与运行时开销。
- Qlib 汇总单证券结果，再拼接和重排列。40 只证券的小批量探针确认，列重排产生不共享数值内存的副本。
- LightGBM 的 `num_threads=2` 不限制 Qlib。诊断时 Qlib 为 `kernels=10`、`joblib_backend=multiprocessing`。
- Linux 环境总内存约 7.65 GiB；容器 `memory.max=max`，不代表环境内存无限。此次 OOM kill 计数从 1 增至 2，容器记录峰值约 6.85 GiB。
- 当前共同股票池的证券并集约 1108 只，池内截面行约 26.9 万。最终研究数据明显小于读取的原始全市场面板。

主要原因是全量面板及临时副本叠加多进程开销。具体被杀的分配点未捕获；前阶段内存残留的贡献尚未确认，不能作为已证实原因。

## 2. 目标处理流程

```text
固定每日股票池 → 证券并集排序 → 每批 64 只证券
                                  ↓
                        Qlib 计算当批完整历史
                                  ↓
               用完整价格生成原始标签，再按每日股票池过滤
                                  ↓
                  特征/原始标签分片落盘，释放当批数据
                                  ↓
                 汇总小型标签表，按完整日截面 CSRankNorm
                                  ↓
              每次只加载当前 Fold 的 train/valid → 训练
                                  ↓
            保留模型、释放训练数据 → 加载 evaluation → 保存结果
```

首版保持单组串行。分片完成后不再拼接全市场原始大表，也不将所有 Fold 的 learn/infer 特征副本常驻内存。

## 3. 修改范围

| 位置 | 计划修改 |
|---|---|
| `backend/app/research/qlib_runtime.py` | 特征读取增加可选 Qlib 并行参数；实验调用显式设置 2 个进程 |
| `backend/app/experiments/search_runner.py` | 分批准备、分片缓存、按 Fold 加载；不再返回全时期 learn/infer 大面板 |
| `backend/app/experiments/search_plan.py` | 校验并记录读取批大小、Qlib 并行度与缓存 schema 版本 |
| `backend/configs/experiments/` | 明确实验的数据准备参数，所有晋级阶段保持一致 |
| `backend/tests/test_experiment_search.py` | 新旧数值对照、跨批标签排名、边界覆盖、恢复和有界加载测试 |

必要时把分片读写与加载实现提取为独立模块，让 runner 负责调度。具体文件划分在实施时确定，不改变现有评估与报告指标定义。

### 3.1 Qlib 并行度

拟增加兼容性接口：

```python
read_features(..., kernels: int | None = None)
```

实验调用显式传 `kernels=2` 并传给 `qlib.init`；其他已有调用不传参数时保持原行为。将它与 LightGBM 的 `num_threads` 分别命名、校验和记录。单独降低 Qlib 进程数不是完整修复，仍需消除全量面板峰值。

### 3.2 按证券分批

1. 复用已冻结的每日股票池，取全部所需日期的成员并集，并按稳定顺序排序。
2. 初始批大小为 64，只对当前批调用特征读取。
3. 首版保留快照原有完整起止区间，避免同时引入日期裁剪与滚动窗口边界变化。
4. 生成原始标签后，按每个截面日的实际成员过滤，写出分片并释放当批对象。

64 只证券 × 487 日 × 361 列 × 4 字节约为 43 MiB，仅为单份数值数组估算；实际峰值必须实测。不能把批大小当作内存硬上限。

当前 Alpha 特征按单证券历史计算，允许按证券拆批。未来若新增跨证券特征，必须重新评估此假设。

### 3.3 标签和处理器一致性

必须保留现有定义：

```text
label(t, h) = close(t+h+1) / close(t+1) - 1
```

- 先使用完整价格序列生成未来标签，再过滤截面日股票池。证券未来退出股票池，不能导致其未来价格被提前删除。
- 保留 provider 的证券有效日期范围、缺失值和日历语义；从 `instruments="all"` 改为显式证券列表时，验证上市区间及边界行为等价。
- 特征分批写出；原始标签可以分批计算，但归一化必须在汇总后，对同一天的完整有效股票截面执行。
- **不能在每个证券批次内独立执行 `CSRankNorm(label)`**，否则标签排名会随批大小改变。
- 沿用原有 InfToNaN、DropnaLabel、CSRankNorm 的顺序和数值语义；评价使用原始标签，训练使用归一化标签。
- `(datetime, instrument)` 是唯一对齐键，确保无重复、无错位，显式验证 train/valid/evaluation 的索引与列顺序。

## 4. 分片缓存与恢复

建议缓存结构如下，文件名属于设计草案：

```text
<cache-id>/
  manifest.json
  universe/
  alpha360/
    shard-plan.json
    batch-0001/
      features.parquet
      raw-labels.parquet
      complete.json
    batch-0002/
      ...
    labels-h5.parquet
    labels-h10.parquet
    labels-h20.parquet
    complete.json
```

设计要求：

- 缓存保存池内特征一份，不重复持久化等尺寸的 learn/infer 特征面板；标签表分别保存原始和训练用值。
- 特征分片跨 horizon 复用。原始价格读取时生成计划需要的标签；标签配置属于缓存身份。
- 写任何分片前先生成不可变的 `shard-plan.json`，记录缓存身份、分片 schema 版本、排序后的预期证券全集、批大小、预期批次数，以及每个 batch ID 对应的有序证券列表和列表摘要。恢复时必须先验证该计划身份，不允许根据磁盘上已有目录反推计划。
- 每个分片写临时文件，完成后原子替换，并记录文件校验和、行数、日期范围、证券列表与 schema。
- 分片集合必须同时满足：batch ID 连续且与计划完全相等；每个证券只出现一次；所有分片证券集合的并集严格等于预期证券全集；分片内及跨分片 `(datetime, instrument)` 索引均无重复；实际行数和证券列表与各分片完成标记一致。缺少、重复或出现计划外分片都视为缓存无效。
- 所有预期分片和全部预期 horizon 的日截面标签归一化完成后，才写数据集级完成标记。该标记必须包含 `shard-plan.json` 摘要、按 batch ID 排序的完整分片摘要列表、预期 horizon 列表及每个标签文件摘要；验证器不能只检查标记中碰巧列出的文件。
- 恢复时校验并跳过完成分片；损坏或未完成分片不得作为有效输入。保留失败证据，采用新尝试目录或明确的恢复策略，不覆盖已验证产物。
- 正常异常记录阶段、批次和安全的异常信息。系统 OOM 可能无法执行异常处理，恢复检查需识别无完成标记的中断，不能伪造成功。
- 保留锁规则：仅在确认原进程退出后，由明确授权的恢复操作处理具体旧锁，不自动抢占。

Parquet 的作用是缓存和持久化。仅更换文件格式、写出后再全量读回，不能降低生成大表时的峰值。

## 5. 按 Fold 有界组装、加载和释放

准备阶段返回轻量缓存引用，而非全时期 learn/infer 内存对象。Fold 组装采用“先确定最终行索引和形状，再逐批填充唯一目标矩阵”，禁止收集分片 DataFrame 后执行全量 `concat`。

### 5.1 预先确定行索引

只读取窄标签表、股票池和日期字段，建立当前 Fold 的三个有序索引：

- train/valid 只保留标签有效的行，保持现有 `DropnaLabel` 规则。
- evaluation 保留股票池中的全部预测行，不因标签缺失而删除，尾部标签未成熟仍可输出预测。
- 三类索引都按 `(datetime, instrument)` 稳定排序；特征列顺序固定为 FeatureSet 定义顺序，类型固定为 `float32`。

索引建立完成后即可得到最终矩阵行数。标签按唯一索引直接重排为向量，不与宽特征 DataFrame 执行 `merge`。重排必须检查缺失键、重复键和意外多出的键。

### 5.2 一次分配最终矩阵

为当前阶段一次性分配最终数组：

```python
X_train = np.empty((train_rows, feature_count), dtype=np.float32)
X_valid = np.empty((valid_rows, feature_count), dtype=np.float32)
```

同时为每个目标矩阵维护写入位图。矩阵创建后不得再创建同尺寸的 pandas 特征副本。当前最大 expanding Fold 约 19 万训练行，Alpha360 单份最终训练矩阵约 261 MiB；该数字只是数值数组估算，不包含验证矩阵、索引和 LightGBM 内部缓冲。

### 5.3 流式扫描并直接填充

使用 PyArrow Dataset/Scanner 或等价的有界读取接口扫描 Parquet 分片：

- 在读取层下推 Fold 日期过滤，只选择索引列和本次需要的特征列；禁止完整读取分片后再过滤。
- 初始扫描批大小为 4096 行，扫描线程和预取队列显式设为有界值并写入运行记录。
- 每批建立 `(datetime, instrument)` 键，通过目标索引取得写入位置，将特征直接复制到最终 NumPy 矩阵；处理完成后释放该批。
- `get_indexer` 返回 `-1` 时立即失败，不能让它写入最后一行；同一位置第二次写入立即失败。
- 扫描结束后，写入位图必须全部为真，实际写入行数必须等于预期行数。
- 保留原有 NaN 语义；只检查索引完整性，不把特征 NaN 误判为未填充。

实现中禁止以下模式：

```python
parts = [pd.read_parquet(path) for path in shard_paths]
frame = pd.concat(parts).sort_index()
```

也禁止填充最终矩阵后再构造、排序或合并一张同尺寸的宽 DataFrame。批大小只约束扫描临时内存，不代表整个 Fold 的内存上限。

### 5.4 训练与评价分开驻留

每个 Fold 按以下顺序执行：

1. 组装 train/valid 最终矩阵和标签向量。
2. 直接用 NumPy 数组构建 LightGBM Dataset，训练并保存模型与学习曲线；训练接口另外接收日期索引和特征名，不能为了兼容旧接口重建宽 DataFrame。
3. 显式释放训练/验证数组、LightGBM Dataset、回调闭包和其他面板引用。保留 Booster；若内存实测不回落，再评估将每个 Fold 放入独立子进程。
4. 单独分配并流式填充当前 evaluation 矩阵，预测、评价和写出结果后释放。

LightGBM 构建 Dataset 时仍可能复制或转换输入，其峰值需要单独测量；本方案不宣称零复制或已实现 LightGBM 外存训练。

训练并发固定为 1，`workers>1` 一律拒绝。分片缓存搬入 direct 入口后每个 trial 各自装载 segment，不再共享一份只读面板，因此并发不再是「验收后可开启」的开关，而是需要重新设计才可能恢复的能力。

## 6. 实施和验收顺序

### A. 先锁定数值语义

在小型 fixture 上建立旧路径参考，测试：

- 特征列名、类型、索引、NaN 位置和有效数值一致。
- h=5/10/20 的原始标签及归一化标签一致。
- 更换批大小、批次顺序，结果不变。
- 同一天成员跨批次时，排名仍是全截面排名。
- 证券中途进出股票池、上市区间、缺失价格、尾部标签未成熟等边界一致。

### B. 实现分批准备和恢复

增加测试，断言每次读取证券数不超过批大小，且没有回到 `instruments="all"` 的大表读取；注入缺失批次、重复证券、计划外批次、重复索引、分片中断和校验和损坏，验证完整集合校验逐项拒绝这些缓存，恢复不会读取半成品或改变结果。

### C. 实现 Fold 按需加载

验证每次只扫描指定 Fold 和必要列，学习曲线及评价指标保持原语义。增加以下断言：

- 没有持有全部分片的 DataFrame 列表，也没有调用分片全量 `concat`。
- 每个目标矩阵只分配一次；扫描批次处理后不进入累计容器。
- 未知索引、重复写入、漏写行以及意外多出的行都会失败。
- 增加分片数量而保持最终行数不变时，组装临时内存不随分片总数持续增长。
- 分别记录索引准备、矩阵填充、LightGBM Dataset 构建、训练和预测阶段的内存峰值。

完成后清理测试插桩，不留生产调试日志。

### D. 真实 Alpha158 对照

先复跑旧结构首组 `804088b1f61ae87cc6f9`，比较预测键、分数、逐日指标与最佳迭代。沿用已约定的 `1e-9` 绝对容差；发生差异先定位，不通过放宽容差掩盖变化。

原始基线在新代码身份下也应重新验证，才能宣称新实现通过原有复现门槛。

### E. 真实 Alpha360 有界验证

先使用一个独立、只包含一组 Alpha360 的验收配置运行完整三 Fold。由实验进程之外的监控器每秒采样 cgroup `memory.current`、系统 `MemAvailable`、阶段、耗时和磁盘增长，并在开始时记录 OOM 计数。进程树 RSS 只作诊断，不能简单相加后冒充物理内存；历史 `memory.peak` 不作为本次独立峰值。

当前约 7.65 GiB 环境使用以下预先冻结的预算：

- 目标峰值：`memory.current <= 5.5 GiB`。
- 警戒线：超过 5.5 GiB 即记录阶段和连续样本，但不中断。
- 安全中止线：`memory.current > 6.0 GiB` 或系统 `MemAvailable < 1.55 GiB` 连续 3 个一秒样本。监控器向试验发送可处理的终止信号，等待限定宽限期后才强制结束，并将该次尝试记录为 `resource_limit`，不得写成功标记。
- 若运行环境总内存变化，必须在启动前重新冻结数值预算；不能在看到运行结果后调整阈值。至少保留 20% 总内存且不少于 1.25 GiB 的系统余量，取更严格者。

监控记录必须覆盖 Alpha360 分片准备、标签汇总、每个 Fold 的索引准备、矩阵填充、LightGBM Dataset 构建、训练和预测。单次运行通过后再连续运行第二个 trial，验证缓存复用和内存回落；只验证第一次运行不足以通过资源验收。

完成条件：

- 三个 Fold 与全部计划评估日期完整输出，模型、曲线、预测和校验和通过。
- 两个连续 trial 均无新增 OOM、未触发安全中止线，且数据准备跨批次的驻留内存不随已处理分片数持续增长。
- 峰值不超过 5.5 GiB；若仅达到 5.5～6.0 GiB 警戒区，即使任务完成也不通过当前环境的资源验收。
- 独立单-trial 验收配置首次完成后，再执行同配置 `--resume --max-trials 1`，必须返回 `attempted=0`；其 success 指针、attempt 数和所有文件校验和必须不变。
- 正式多-trial 计划的恢复具有不同语义：允许继续运行下一个 pending trial。恢复前后对已完成 trial 保存 success 指针、attempt 数和文件校验和快照，确认它们完全不变；不能以正式计划返回 `attempted=0` 作为验收条件。
- 监控采样、阈值、触发结果和各阶段峰值写入验收记录，不能只报告最终最大值。

### F. 恢复正式搜索

代码与缓存 schema 变化后建立新实验身份。保留旧 12 组和中断证据作对照，在新目录运行完整 24 组，不把不同实现版本的产物混成一个搜索。完整结构阶段通过后，才按既有流程选择候选并进入参数搜索。

## 7. 非目标与后备选择

- 不缩短历史、验证窗口或 purge，不删掉 Alpha360，不减少特征列来取得表面成功。
- 不改变数据库/provider 内容，不修改已有成功产物，不发布模型或执行交易。
- 增加运行环境内存是后备选择，不替代对不必要副本和全量读取的治理。
- 核心分片、按 Fold 加载、单 worker 限制及外部内存监控已经实现；Alpha360 的内存门槛已实测达标，D 步复现比较与 F 步正式搜索仍按第 6 节执行。
