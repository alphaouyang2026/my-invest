# 16 — 同步恢复执行与数据重新校验

**What to build:** 补齐同步失败后的恢复路径，并新增一个独立的「重新校验」能力。恢复执行方面：尝试次数耗尽后目前是死胡同（`is_resumable` 返回 false、前端不显示任何按钮），新增强制重试端点打破它。重新校验方面：用当前质量规则对最新同步的数据重做 04 的判定并产出新快照，使规则演进后无需重抓数据即可重验。findings 的锚点从「同步运行」改为「一次质量评估」，同步与重新校验共用该概念。

**Blocked by:** 04 — 点时版本、数据质量校验与数据快照

**Status:** ready-for-agent

## 三个功能的划分

本票的用词以此为准，不再使用"重放"这个说法（它把快照当成可挑选的操作对象，凭空引入了"选哪个快照"这一层，而实际模型里没有这层）：

| # | 名称 | 含义 |
|---|---|---|
| 1 | **同步** | 现有的 `sync now`。本票不改 |
| 2 | **恢复执行** | 失败的同步，从失败处接着跑。已有大半，本票补死胡同 |
| 3 | **重新校验** | 用当前规则，对**最新同步的数据**重做 04 的质量判定 |

功能 2 已经存在的部分（本票不重复实现）：批次级检查点、`plan_fingerprint` 校验、worker 崩溃后自动重排、手动 `/resume` 端点与前端按钮、`_reset_unpublished_batches`。

## Acceptance criteria

- [ ] `POST /data-sync/runs/{id}/force-retry` 在一个事务内重置 `attempt_count=0` 并将运行退回 `queued`，复用 `resume` 的批次重置逻辑；适用于 `failed`/`partial_failed`/`cancelled`
- [ ] 前端在「更多」中展示失败原因摘要与已尝试次数，旁附「强制重试」；无二次确认弹窗
- [ ] 新表 `quality_evaluation` 承载评估身份、状态、错误与所用策略快照；`quality_findings` 改挂 `evaluation_id`，唯一约束为 `(evaluation_id, rule, trade_date)`
- [ ] 新 task_type 执行重新校验，与同步互斥；创建时若该 source 有活动任务则拒绝并返回已有任务
- [ ] 重新校验产出新快照（同 cutoff、同 master、version 递增），head 前移；旧快照的 findings 与判定不被改写
- [ ] 结论与上次相同时仍产出新快照
- [ ] 前端在快照区块标题行旁提供「重新校验」入口，并展示评估状态
- [ ] 迁移为非破坏性：为现存同步补建 `quality_evaluation` 并重挂现有 findings，行情数据不动
- [ ] 测试覆盖尝试耗尽后的强制重试、重新校验产出新快照、重新校验与同步互斥、迁移回填

## Design decisions

经 `/grilling` 会话确认（Q1–Q22），实施前定稿。

**功能 2 · 恢复执行**

- 独立端点 `POST /runs/{id}/force-retry`，**不是**给 `resume` 加 `force` 参数。正常续跑与推翻终态判决的风险等级不同：前者随时可点，后者要求人先确认死因。独立端点也让将来加权限或确认逻辑有地方落。
- 只重置 `attempt_count` 而不改运行状态是不行的——中间态是「计数已清但运行仍是终态」，用户点第二下之前系统处于一个没人定义过的状态。必须在一个事务里两件事一起做。
- 适用于 `failed` / `partial_failed` / `cancelled`。`succeeded`/`no_change` 归功能 3。
- **不设二级上限**。人工确认已经是最强的节流，再加一个数字上限只会制造第二个死胡同——正是本票要消灭的东西。
- **不做任何形式的退避**（固定延迟、指数退避均不做）。理由：强制重试消除死胡同后，「三次机会几秒内烧光」不再致命，只是多点一次按钮；而退避对主要失败模式无效——能杀死整个 worker 进程的基本只有 OOM、宿主重启、数据库不可用，前两类退避帮不上；J-Quants 的限流/超时/5xx 在 adapter 层（`RetryPolicy`，5 次、指数退避、遵守 `Retry-After`）就被吸收，根本到不了任务重试这一层。
- **已知并接受的两个代价**：
  - **计数器数的是「被领取次数」而非「失败次数」**：`_claim_next_task` 领取即 `attempt_count += 1`（`runner.py:170`），worker 停止时任务卡在 `RUNNING`，下次启动被 `recover_orphaned_tasks` 退回队列、再被领取时又加一。三轮之后 `runner.py:136` 判定超限并写成终态。因此首次全量同步（约 14 小时）期间 `docker compose restart worker` 三次，会杀掉一次数据、API、代码都没问题的运行。可用强制重试救回。
  - 复活一个陈旧计划不做拦截。被取消的运行冻结的是当时的目标日期，两个月后复活会产出覆盖范围看着新、实际停在旧日期的快照，且该错误是静默的。
- UI 收在「更多」内，展开后显示失败原因与已尝试次数，旁附按钮，无弹窗。语义上它是推翻系统已下的判决，不该与「立即同步」并排；但单用户本地系统里弹窗只是仪式，把该看的信息摆在按钮旁边比事后问「确定吗」有用。

**功能 3 · 重新校验**

- 作用对象是**当前最新数据**（head 快照），**不是**可挑选的快照。UI 上是一个全局操作，不是快照列表里的逐行按钮。
- 产出**新快照**：沿用 head 的 `bar_publish_sequence`、`master_snapshot_id`、`calendar_publication_id`，version 递增，重跑质量规则得出新的 findings 与新的 `is_backtest_eligible`；head 前移。形状与 `_inherit_snapshot` 一致，代码路径可复用。
- **绝不原地改写旧快照**——04 已定判定创建时算一次、永久冻结，且已绑定回测的快照不得被后续修订改变。新旧并存还让「规则改动带来了什么变化」变得可对比。
- head 前移不构成倒退：新旧快照 cutoff 相同，覆盖范围不变，只是判定更新。
- 结论与上次相同时**照样产出新快照**。定义「结论相同」需要判断 findings 是否逐条相同、规则代码变了但结果碰巧一样算不算——每种定义都会在某个边界上骗人。代价只是一行快照记录，换来每次评估都留痕。
- 走 Task 队列，**新 task_type**，不复用 `jquants_sync`（那会让同步的活动任务互斥逻辑把重新校验也算进去，反而堵住同步；且 `SyncRun` 状态机对重新校验不适用）。
- 与同步**互斥**。理由不是并发（单 worker 天然串行）而是语义：同步跑到一半时快照尚未生成，此时排队一个「校验该快照」的任务，等它执行时对象状态已经变了。
- **不可同步执行**。真实数据下质量 pass 要在 210 万行上跑多个聚合查询，放在 HTTP 请求内必然超时并占住 FastAPI 线程池。

**Schema**

- 新表 `quality_evaluation`：`id`、`kind`(`sync`/`revalidate`)、`sync_run_id`(可空)、`produced_snapshot_id`(可空)、`policy`(JSONB)、`status`、`error_summary`、`created_at`。
- `quality_findings` 改挂 `evaluation_id`，唯一约束 `(evaluation_id, rule, trade_date)`，移除 `sync_run_id` 列。
- **为什么引入「评估」这个概念**：`QualityFinding.sync_run_id` 是 NOT NULL 外键指向 `sync_runs`，而重新校验根本没有 sync run；复用原运行 id 会在第二次校验时撞唯一约束。同步和重新校验都产生**一次评估**，findings 属于评估而非属于运行——这本来就是更准确的建模。改挂 `snapshot_id` 会丢掉 04 特意保留的性质（没走到创建快照就失败的运行仍留下可查原因）；加 `replay_id` 列则让唯一约束变成三列可空组合，日后无人看得懂。
- `quality_evaluation` 同时兼任重新校验的**进度记录**，不另建仿 `SyncRun` 的状态机表。重新校验没有阶段可分——它就是一趟聚合查询，没有日历、批次、分页、限流这些把 `SyncRun` 撑复杂的东西。
- `policy` 存 `QualityPolicy` 的 JSONB 快照（关键字段清单、升级阈值、复权容差、样本上限）。**注意其论据是未来时**：今天生产环境从不注入自定义策略（`tasks.py:21` 与 `get_sync_workflow()` 都用默认值），所以代码版本等价于策略内容；但 14 号 ticket 明确要做质量阈值的用户可编辑界面，那天起同一份代码就能跑出不同阈值。之所以现在就加，是因为它便宜到不值得推迟——一个 JSONB 列、写入时一行 `asdict(policy)`——而 14 号落地前产生的评估记录事后永远补不回当时的阈值。

**迁移 —— 本次不 purge**

- 04 那次清空是正当的：被清掉的 `quality_status` 全是默认值、从未被任何规则评估过，留着等于让数据库断言一件假事。**本次情况相反**——库中约 214 万行行情是耗时约 14 小时抓取且已被真实评估的数据。
- 做法：为现存那次同步补建一行 `quality_evaluation`（`kind=sync`，指向原 `sync_run_id` 与其产出快照），将现有 findings 重挂到它上面，再删除 `sync_run_id` 列。行情数据完全不动。
- 回填是确定性的：现存恰好一次同步、一个快照、一批 findings，三者一一对应，无歧义。

**明确不做**

- 任何形式的退避
- 批次内的日期级检查点。批次是 publication 的原子单元（03 立起的核心不变量），改为日期级等于取消批次概念，publication 从 98 个变成 486 个。而实际代价比看上去小：批次内已抓到的 `bar_versions` 行**已经落库**，只是因 publication 未发布而不可见，续跑重抓时相同内容哈希会命中已有版本行直接复用，不会重复。真正浪费的只有 API 调用——最坏情况（第 5 个日期失败）重抓 4 次，按 `RetryPolicy.min_interval_seconds = 15.0` 算约 1 分钟。拿核心不变量的解体换最坏一分钟，不划算。**这是设计不是缺陷**，记录于此以免日后有人看到「失败一次要重抓 5 天」当成 bug 去修，而修法恰好会拆掉 03 的原子性保证
- 陈旧计划拦截（Q13 明确由用户承担）
- 强制重试的次数上限
- 按死因区分是否计入尝试次数。**这是"选择不做"，不是"做不到"**：`docker compose restart` 发的 `SIGTERM` 可以捕获，理论上能把「被优雅关机打断」标记成不计入；但 OOM 的 `SIGKILL` 与断电无法捕获，所以只能分一半。取舍是「补一次点击」对「引入信号处理逻辑并接受它只覆盖一半情况」，选了前者
- 质量阈值的用户可编辑界面 → 14

**会话中推翻或作废的**

记录于此，以免日后有人重走一遍：

1. **「重放」这个概念作废**。它把快照当成可挑选的操作对象，凭空引入了"选哪个快照"这一层复杂度；实际模型中重新校验永远作用于最新数据。由此产生的两个问题（重放旧快照是否让 head 倒退、是否只对不可用快照开放）随之作废。
2. **指数退避的推荐被收回**。原动机来自一次 OOM 导致的连续崩溃，但退避对那次毫无帮助——OOM 在该数据量下是确定性的，退避只会把同一失败推迟十几分钟。用一个退避解决不了的案例论证退避，是推理漏洞。
3. **`policy` 留痕的原论证被收回**。原称「同一份代码可能跑出不同阈值」，核查生产路径后确认今天不成立，理由改为未来时（14 号 ticket）。
